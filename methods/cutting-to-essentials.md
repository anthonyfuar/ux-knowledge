# Cutting to essentials

## Use when
- Simplifying design w/o losing any function = Occam's Razor on screen / flow.
- Team leans toward more complex option.
- Procedure = 7 steps.

## Steps
1. **Start w/ simplest solution that could work.** Keeping complexity out beats removing it later.
2. **Question each element: needed?** Shrink test: keep stripping interface; floor = last cut before content stopped conveying message / people could no longer locate it.
3. **Challenge "delight" additions.** Keep only if it removes barriers for people; cut if it adds barriers.
4. **Prune hard; function stays whole.** Delete what neither contributes nor signifies; if plainer equivalent exists → swap in.
5. **Run regular peer critiques.** Designer explains each choice aloud; peers respond + discuss.
6. **Cut until every remaining part essential, then stop.** Maxim: the better the design, the less of it.
7. **If team prefers complex option → suspect complexity bias.** Freeze assumption list; reopen only after team returns to problem: watching it happen + experiencing it first-hand.

## Decision rules
- If unsure element needed → step 2 shrink test decides: message + findability survive w/o it? Yes → cut.
- If delight addition adds barrier → cut; if it removes one → may stay.
- If simpler version of element exists → swap in.
- If design part resists justification in critique → likely ineffective / unclear part (usually so) → rework / cut.
- If each new problem explanation rests on yet another assumption → stop adding; first return to problem: watch it happen + experience it first-hand.

## Evidence
|Finding|Study (year, kind, sample)|Strength + caveat|Design consequence|
|---|---|---|---|
|Shown sample number triple, most people proposed elaborate rules; hidden rule = any three ascending numbers|1989 complexity-bias study, number-triple task|"most", not all|When team favours elaborate solution → check if plain one already fits observations|

## Pitfalls
|Symptom|Likely cause|Fix|
|---|---|---|
|Complexity removed late|let in early|step 1: begin simple, prevent entry|
|Delight additions pass review unexamined|"delight" not challenged|step 3 barrier test|
|Choices nobody can explain aloud|no critique habit|step 5 peer critique|
|Endless polishing, no stop|no stopping rule|step 6: done once every remaining part essential|
|Team picks elaborate option by default|complexity bias|step 7: no new assumptions w/o observation|

## Hypothetical example
- Hypothetical: city transit ticket kiosk adds spinning 3D ticket preview before payment + hides route search behind swipe gesture. Both add barriers → cut. "repeat last trip" button skipping re-entry removes barrier → may stay.
