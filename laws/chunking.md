# Chunking

## In one line
Chunking = turning information fragments into meaningful units. Short-term memory caps meaningful-unit count, not raw bits → grouping lets more fit. Matters most in information-dense experiences.
- Class: construct (not effect, not principle). Aliases: none. Theme: Memory.
- Reaches furthest into: content modules + dividers, headings + line length, input formatting (phone numbers, card numbers).

## Applies when / does not apply when
|Situation|Chunk for memory?|Why|
|---|---|---|
|Users hold in mind + retype (codes, IDs, phone numbers)|Yes: memory-sized groups|limit = meaningful units|
|Users memorize + transfer string (confirmation numbers, license keys) in high-distraction settings (in-car use, kiosks, clinical work)|Yes, especially there|string must survive transfer|
|Users search/scan/compare|No memory-sized splitting; visual grouping still aids scanning|grouping = structure here, not memory relief|
|Visible navigation|Memory capacity: no argument for capping item count|scanned, not memorized|
|Screen of many independent settings|Cite Cognitive Load + Selective Attention + Chunking + progressive disclosure (Tesler's Law: relocates complexity); not Choice Overload|load = scanning + finding, not one choice among substitutes|

Rule of thumb: visual grouping aids scanning; memory-sized pieces only for what users must hold in mind + retype.

## Decision rules

### What to chunk, and when
- If users must memorize + carry string elsewhere (code, ID, confirmation number, license key, phone number) → chunk; especially in high-distraction settings (in-car, kiosk, clinical).
- If users search/scan/compare → no memory-sized batches; e.g. ~five-results-per-page cap only adds paging + comparison work. Keep comparable items side by side.
- If content optional / users can discard it (e.g. optional form fields) → own block from first render.
- Group content when shown, not afterwards.

### How to build chunks
- Building blocks by target: prose → moderate line + overall length, headings; strings → delimited groups (codes, IDs, card numbers); layout → importance order anyone can see, separate-looking modules, section dividers.
- If passage arrives as one undivided mass → moderate line + overall length + headings; same text then beats unbroken block.
- Delimiting string (e.g. booking reference) + paragraphing prose = one grouping move → same chunking logic governs both.
- Chunk along meaning users already own (dates, familiar formats, known categories); arbitrary groupings → little gain.
- Give ready-made, familiar groupings (dates, standard formats); avoid groupings users must build: chunk helps only once recognized.
- Order in-group items so linking rule visible.
- If users must recall items as separate things → mix types / sub-group; avoid uniform run of one kind.
- Pre-chunk for users: learned groupings fit more under same memory limit.
- Never make users translate/convert code while holding it in mind → show final, familiar form.
- Grouping needs visual distinctness + hierarchy; w/o them most benefit lost.
- To match people's instinctive stock-taking of screen contents → make groups look separate + importance order obvious. Hierarchy, dividers + modules expose how content pieces relate.
- Payoff: chunked content → goal-relevant parts found + used sooner; easier skimming.

### Long flows
- Long flow = sections containing steps; visible breaks at chunk boundaries; parts in coherent order, never interleaved.

### Experts vs novices
- Experts can use denser screens; novices need progressive disclosure / simpler mode.
- Experts + novices chunk one screen differently → test dense expert tools w/ both.

### Categories and labels
- Name categories at most specific level users know; use typical members as examples, placeholders + icons.
- Label on item/state/chart shapes later memory of it → names + summaries must stay accurate.

## Why it works

### Mechanism
- Short-term memory limited by meaningful-unit count, not raw bits → grouping fits more.
- Visual grouping + hierarchy work by mirroring how people scan.
- Chunk (2004 definition) = elements strongly linked to each other, only weakly to other chunks' elements.
- Chunks sit in long-term memory; used to rebuild degraded short-term traces.
- 2021 account: recall = Bayesian inference, known chunks as priors → familiar acronym easier to recall than random letter string.
- Chunks personal; typically two to six items. Chunk makeup varies w/ language, culture + prior knowledge.
- Chunking acts like data compression of redundant material. 2016 research: two factors = compressibility (can one rule sum up items?) + order (does sequence reveal it?).
- Linear-looking behaviour hides hierarchical plan. Chunk hierarchy: if low-level link breaks, higher-level nodes still reach later parts; flat chain: one broken link strands all after it.
- Chunking rides on expertise, not larger memory capacity.
- While people learn skill, chunk levels overlap; message capacity grows as each chunk holds more.
- Most common form = verbal recoding (material put into words). People keep own summary/label, not original, + later fill in details fitting label.
- Recoding pays only when translation nearly automatic; otherwise next group lost while previous one converted.
- Category checks: membership in small, specific category confirmed faster than in broad one; typical members faster than atypical.

### Origin
- Term from 1956 paper on how much people can tell apart + recall at once, written when psychology first took up information theory.
- Short-term memory = exception this paper singled out: ceiling in meaningful units, whereas some tasks there behaved like steady-capacity information channel measured in bits.
- Miller's Law (7 plus or minus 2) + term chunking: same 1956 paper; it put ceiling near 7 items for both absolute judgment + immediate memory span.
- Real emphasis = chunking, not number seven.

## Misreadings and limits
- Wrong: Miller's Law's seven caps items per screen → Right: seven = reason to chunk, not screen limit.
- Wrong: cap menus, results, dropdowns, slides / radio groups at five to seven items per Miller's Law → Right: 2000 critique called this superstition; working-memory capacity may sit nearer four than seven; on-screen options recognized, not memorized → memory span does not limit them.
- Wrong: chunk/paginate content users scan/compare → Right: chunk what users memorize + transfer; keep comparable items together.
- Wrong: expert density + expert groupings help novices → Right: chunk works only if user already knows pattern; expert-natural groupings give novices little benefit → progressive disclosure / modes.
- Wrong: cite Choice Overload for screen of many independent settings → Right: Choice Overload needs one choice among close substitutes; sixty separate toggles = scanning + finding load → cite Cognitive Load, Selective Attention, Chunking + progressive disclosure (Tesler's Law).
- Wrong: cite 1956 paper for magic count → Right: cite it for "group information meaningfully".
- Wrong: date paper 1958 → Right: 1956 (sometimes misdated 1958).
- Limit: chunk helps only if user recognizes group as group.
- Limit: grouping w/o visual distinctness + hierarchy loses most benefit.

## Check questions
- Chunks easy to scan, plain hierarchy? (Chunking, Miller's Law) Look for: walls of text, unformatted numbers/codes, dense layouts w/o modules/dividers.
- Option count low at every step, drawn-out / multi-part tasks staged as sequence? (Chunking, Cognitive Load; Hick's Law only for choices inside each step) Look for: one huge form or settings page.
- Every string users must retype in delimited, familiar, final form?
- Optional content in own block from start?
- Comparable items kept together, not paginated into memory-sized batches?
- Dense expert tool tested w/ both novices + experts?

## Symptoms → fixes
|Symptom|Likely cause (laws)|Fix|
|---|---|---|
|Layout reads as undifferentiated clutter|Chunking, Common Region, Prägnanz|evident hierarchy, dividers, modules w/ backgrounds/borders|
|Codes/IDs copied from elsewhere get mistyped|Chunking, Working Memory|delimited groups of 3-5 characters; accept paste; code visible where entered|
|Settings page w/ dozens of toggles hard to scan|Cognitive Load, Chunking, Common Region, Tesler's Law via progressive disclosure, Pareto Principle (check usage w/ analytics); not Choice Overload|task-based labelled groups; search across setting names, synonyms + descriptions; advanced settings behind disclosure|

## Hypothetical examples
- Hypothetical (order reveals rule): medication reminder lists doses morning, noon, evening, bedtime → reader compresses to "through the day"; same doses shuffled → no rule to compress, though items identical.
- Hypothetical (chunk levels grow w/ skill): new hire learning accounting-tool keyboard shortcuts first treats each key as one unit, then each key combination, then whole multi-step sequence as one move.
- Hypothetical (delimiters): rail booking reference can appear as one unbroken run, w/ spaces between groups, or w/ spaces + hyphen between segments; each added delimiter → groups easier to see + retype.
- Hypothetical (specific category): hardware store app files cordless drills under "Power drills", not "Tools" → shoppers can confirm right place sooner.
- Hypothetical (typical member): public benefits portal illustrates "Income support" category w/ its most common benefit, not rare one-off grant.
- Hypothetical (visible modules): smart thermostat app splits controls into Schedule, Modes + Energy modules, each w/ heading + divider.
- Hypothetical (dense but grouped): school attendance console packs many figures yet stays legible: each class = separate module, same internal layout.
- Hypothetical (spaced result chunks): library catalogue shows each result as spaced block, same internal order: title → creator line → availability.

## Humane bound
- No recorded case of chunking turned against people; general influence-vs-manipulation test applies.
- Recorded caution: people keep own summary/label + later fill in fitting details → UI label on item, state or chart shapes later memory → names + summaries must stay accurate.
- Bound by Transparent: labels + summaries must stay accurate.
- Bound by Inclusive: chunks vary w/ language, culture + prior knowledge.
- Further reading for this bound: using psychology responsibly; inclusive + accessible design patterns.
