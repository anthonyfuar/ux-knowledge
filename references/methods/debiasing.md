# Debiasing research, reviews and the design team

## Use when
- Planning study, writing results, running review, checking team's own judgment for bias.
- Two lists: research, reviews + reports (9 points) · design team (5 points).
- Rule: match debiasing tool to problem at hand.

## Research, reviews + reports
|Do|Why / evidence|
|---|---|
|Ask neutral questions, never leading ones.|Wording shifts answers: asked if happy w/ social life → more satisfaction reported than asked if unhappy. One child-custody vignette: same parent chosen by most respondents asked whom to award custody, rejected by most asked whom to deny it.|
|Before seeing results: write hypothesis, design tasks that could disprove it, fix success criteria.|No criteria fixed in advance → unwelcome findings face higher proof bar than welcome ones (disconfirmation bias).|
|Collect each person's independent judgment before group discussion.|Stating position aloud after each evidence piece → steadily more confident in first view; answering only at end → no polarization.|
|Explicitly ask for balanced pros + cons case.|One study: explicit request → measurably more opposing information included.|
|Run pre-mortem: imagine launch failed, ask why.|Steps in premortem.md.|
|Include reviewers valuing accuracy + whose stance presenters do not know.|Accountability research: open reasoning only when expecting to justify view to informed audience of unknown views.|
|Flip every frame before deciding: success rate → failure rate; percentages → number of people affected.||
|Small samples → report counts + confidence intervals, not percentages.|Worked statistic: 16 successes of 20 compatible w/ true success rate ~58% to 93%.|
|Reports: state missing context: site type, feature importance, build cost.||
|Say "not sure yet" when data insufficient for conclusion.||
|Check for incomplete frames (e.g. current users only, not prospective) + too-narrow frames (one benefit judged, others ignored).|Cannot remove frames from decisions; aim = awareness.|
|Judge past decisions by information available then, not by outcome.|Counters hindsight + outcome bias.|

Hypothetical: pharmacy-app interview: "How much did the new refill reminder help you?" presumes it helped → leads participant; "Tell me what happened the last time you reordered a prescription" does not.

## Design team
1. Assume own bias. Why: people spot bias in others far more readily than in selves; those w/ strongest bias blind spot dismiss peer input + gain least from debiasing training.
2. Build external review into process (peer critique, outside facilitators) instead of self-audit.
3. Synthesis + critique: name likely biases; ask what got missed/over-weighted; actively seek disconfirming evidence.
4. Entrenched stakeholder → present facts non-directively + invite alternative; avoid head-on confrontation.
5. Time-box review items by importance. Counters bikeshedding = groups giving disproportionate time to trivial, easy topics.

## Tools
|Tool|Meaning|
|---|---|
|Blind review|Hide proposer's identity while judging idea.|
|Base-rate + reference-class forecasting|Estimate from comparable past projects' outcomes, not inside-view guess.|

More team tools: decision journal, decision matrix, disconfirming-evidence prompts, pre-mortem, red team / blue team, after-action review, A/B tests.
