# Product cases

## Use when
- Scope: real product cases of UX laws in use: redesign rollouts · waits · send moments · search · onboarding · complexity moved to builders · novelty · real content lengths · well-being metrics.
- Open when law / pattern needs concrete real-world case, or to check strength of commonly told product story before citing it.
- Laws shown in use: ../laws/mental-model.md, ../laws/goal-gradient-effect.md, ../laws/hicks-law.md, ../laws/working-memory.md, ../laws/doherty-threshold.md, ../laws/chunking.md, ../laws/proximity.md, ../laws/uniform-connectedness.md, ../laws/teslers-law.md.
- Strength overall: illustrations, not quantified evidence; few rest on controlled studies.

## 1. Rolling out a redesign
|Finding|Source (year, kind)|Strength + caveat|Design consequence|
|---|---|---|---|
|Early-2018 Snapchat redesign triggered mass simultaneous protest on Twitter; part of its user base went to Instagram|public reaction|public reaction only, no metrics|Sudden redesigns cause mental-model discordance|
|Cause of Snapchat backlash: reworked layout put everyday features out of easy reach|↑|public reaction only, no metrics|↑|
|Google Calendar, Gmail + large video platform (in 2017) kept look largely unchanged for years before redesign|product histories|product history, no metrics|Let users migrate to redesign when ready|
|Material Design versions of these three came to desktop as opt-in, w/ way back, way to comment + time to try new design and grow used to it|↑|described outcome: mental-model discordance avoided|Let users migrate to redesign when ready|

## 2. Designing a wait
|Finding|Source (year, kind)|Strength + caveat|Design consequence|
|---|---|---|---|
|Uber Express POOL rider wait screen rests on 3 levers, each tied to something rider sees: animation filling idle time → idleness aversion · each wait stage spelled out → goal gradient · estimated arrival paired w/ how figure derived → operational transparency|2019 behavioral-science work|design case|Treat waits as potential negative peaks of experience|
|Once reworked wait screen ran (Uber Express POOL), riders abandoned already-booked ride 11% less often|2019 A/B experiment|single in-house test|↑|

## 4. Search page + results
|Finding|Source (year, kind)|Strength + caveat|Design consequence|
|---|---|---|---|
|Google Search landing page changed little since its 1998 launch|product history|longevity + adoption only, no study|—|
|Google Search cited as single flow where these laws act together: Doherty Threshold · Hick's Law · uniform connectedness · working memory · chunking + proximity|↑|longevity + adoption only, no study|Let several laws work together in one flow|

- Hypothetical (one device per law): city-services portal's search. Doherty Threshold → answers return fast + elapsed time reported · Hick's Law → page holds one input w/ cursor already in it; ways to narrow results appear only after first search · uniform connectedness → framed panel binds top answer to its map + opening hours · working memory → suggestions finish typing, + request stays printed above answers · chunking + proximity → white space sets each answer apart as own block.

## 6. Moving complexity to the builders
- Design consequence: Tesler's Law in practice = builders, not users, carry complexity; whatever must stay goes into progressively disclosed layers.
- Support: qualitative only; contrasting minimal control set w/ cluttered set cut down by its users = anecdotal.

|How builders take load|Hypothetical|
|---|---|
|Few controls on device; everything else in on-screen layers opened step by step|Hypothetical: library self-service kiosk shows only "borrow" + "return"; renewals, holds + fines open from on-screen menu when asked for|
|Data already given copied to where needed again|Hypothetical: home-insurance claim form fills incident address from policy address once person confirms damage happened at home|
|Known data entered ahead + likely entries proposed from history|Hypothetical: IT-support ticket form enters requester's name + department from sign-in + proposes devices this person reported before|
|Wording predicted for user|Hypothetical: clinic's patient-messaging tool drafts short candidate replies + offers endings for nurse's half-typed sentence|
|Details kept on file, reused at moment of need|Hypothetical: train-booking app holds traveller's railcard + payment card → repeat booking goes through w/o typing either again|
|Sensing takes over whole manual step|Hypothetical: hospital supply room logs each item carried out by nurse via shelf sensors + camera-based recognition → no scan-out step left|
|Question in everyday words replaces query building|Hypothetical: school district's attendance tool answers typed question on classes w/ most missed days this term, w/o any filter setup|
|Category links stay folded until pointed at / tapped|Hypothetical: city council's site names its services along top; each unfolds its own pages only when touched → residents scan one service at a time|

- Hypothetical: clinic's office manager hides every toolbar of crowded scheduling tool except "book" + "cancel" so temporary front-desk staff can use it on day one → people other than maker strip cluttered tool down to essential controls; maker can ship this essential layer first + disclose rest progressively.
